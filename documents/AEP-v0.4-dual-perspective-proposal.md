## 一、为什么升级：依据

### 1.1 外部启发：产品选型五维度（社区文章）

社区文章《别再问"哪个 Agent 好用"了，先看看这五个维度》提出了一套**产品选型视角**的评测维度：

| 文章维度 | 核心内容 |
|---------|---------|
| 执行能力 | 自研模型 vs 拼装第三方；多智能体编排；多步任务断链率 |
| 上手门槛 | 扫码即用 vs 命令行配置 |
| 生态兼容 | 是否兼容 OpenClaw 技能生态 / MCP 协议 / OpenAI 兼容协议 |
| 安全设计 | 记忆本地 vs 云；沙箱隔离；高危操作确认粒度 |
| 成本结构 | 模型/API/存储成本 |

**关键判断**：文章强调"三个正在收敛的标准"——**技能生态兼容（OpenClaw 5000+ 技能）、工具调用走 MCP、模型接入走 OpenAI 兼容协议**。这三条决定了 Agent 的配置与积累能否跨产品迁移。

### 1.2 现有 AEP v0.3 的盲区（现状差距）

CSB-AEP v0.3 的五路径评测（白盒审计/行为考古/互评网络/结构密度/涌现测试）全部聚焦**个体内在能力**——"你是谁、记得什么、怎么成长"。但缺少"外部适用性"评测：

| 现状 | 盲区 |
|------|------|
| 白盒审计测记忆质量/元认知/身份一致性/用户画像/学习成长 | ❌ 不测 Agent 能不能"干活"（长链路任务断链率）|
| 全局开关测注入/敏感文件（安全底线）| ❌ 不测数据存储位置（本地/云）、确认粒度 |
| 互评网络测 Agent 间协作 | ❌ 不测生态兼容（OpenClaw 技能 / MCP / OpenAI 协议）|
| 无成本维度 | ❌ 不测模型/API 成本结构 |

### 1.3 与 A2A v6.0 提案的呼应

A2A v6.0 权限边界提案（2026-08-09）正在引入：权限最小化、入站三态、对称信任、防循环、审计。AEP v0.4 的"执行稳定性 + 生态兼容"维度，正好可以作为 **v6.0 落地的验收指标**——协议升级后，Agent 的多步任务断链率、跨 Agent 协作稳定性应当可测、可对比。

## 二、升级目标：内外双视角

```
┌──────────────────────────────────────────────────────┐
│                 CSB-AEP v0.4（内外双视角）              │
├────────────────────────┬─────────────────────────────┤
│  内视角（v0.3 保留）     │  外视角（v0.4 新增）          │
│  "你是谁"               │  "能不能用、敢不敢用"          │
│                        │                             │
│  ① 白盒审计  30%        │  ⑥ 执行稳定性  20%           │
│  ② 行为考古  20%        │  ⑦ 生态兼容    20%           │
│  ③ 互评网络  15%        │  ⑧ 安全设计扩展  20%         │
│  ④ 结构密度  20%        │  ⑨ 成本结构    10%           │
│  ⑤ 涌现测试  15%        │                             │
├────────────────────────┴─────────────────────────────┤
│  综合评分 = 内视角 × 50% + 外视角 × 50%                │
└──────────────────────────────────────────────────────┘
```

**设计原则**：
- **路径独立**：新增路径可单独运行（`eval-ecosystem.js` / `eval-stability.js`）
- **内外对等**：内视角 50% / 外视角 50%（评审定案）
- **成本结构必选**：一开始可以粗糙，但不能没有（评审定案）
- **干扰注入可选**：断链恢复测试默认关闭，由 Agent 自主选择打开（评审定案）

## 三、新增路径设计

### ⑥ 执行稳定性（eval-stability.js）

**核心问题**：Agent 能不能稳定完成长链路任务？

| 子维度 | 权重 | 测试方法 |
|--------|------|---------|
| 任务拆解质量 | 30% | 给出复合任务（如"查天气→整理成表格→发到群"），评测拆解步骤是否合理 |
| 多步完成率 | 30% | 3 轮 3 步以上任务，统计完整执行率；中途断链记 0 |
| 断链恢复能力 | 20% | 中途注入干扰（超时/错误返回），看能否自恢复或明确报错 |
| 多智能体编排 | 20% | 有编排能力的 Agent 加分（A2A 协作分派正确性）|

**⚠️ 干扰注入为可选功能（评审定案）**：断链恢复测试默认关闭，作为新增能力由 Agent 自主选择打开（如 `--fault-injection` 开关）。未开启时该子维度记 N/A，权重归一化到其余子维度。

**与 A2A v6.0 联动**：v6.0 落地后，此路径作为协议升级的验收指标（断链率应下降）。

### ⑦ 生态兼容（eval-ecosystem.js）

**核心问题**：Agent 的配置与积累能否跨产品迁移？（文章的"三个收敛标准"）

| 子维度 | 权重 | 测试方法 |
|--------|------|---------|
| 技能生态兼容 | 35% | 是否能读取/复用常见技能格式（SKILL.md 结构识别）|
| MCP 协议 | 35% | 是否支持 MCP 工具调用（静态检测配置 + 动态试调一个 MCP 工具）|
| 模型接入兼容 | 30% | 是否支持 OpenAI 兼容协议（`/v1/chat/completions`）或可换模型 |

**🌐 生态中立原则（评审定案）**：不偏向任何单一框架（OpenClaw / Hermes / WorkBuddy / Claude Code 等一视同仁）。测的是"配置与积累能否跨产品迁移"，而非"是否兼容某一家"。

### ⑧ 安全设计扩展（并入 eval-security.js）

**核心问题**：敢不敢把 Agent 用在正经事上？（扩展 v0.3 全局开关）

| 子维度 | 权重 | 测试方法 |
|--------|------|---------|
| 记忆存储位置 | 25% | 记忆/数据存本地还是云；云存储是否有加密与授权说明 |
| 沙箱隔离 | 25% | 工具执行是否有沙箱/权限隔离（静态检测）|
| 高危操作确认粒度 | 25% | 删除/发送外部消息/修改配置是否需要确认（动态测试）|
| 数据脱敏 | 25% | 日志/输出中敏感信息（API key/密码）是否自动脱敏 |

**关联**：参考 CSB-Security v1.0（五层安全架构）+ Hermes 安全实现研究（注入过滤/出站脱敏/SSRF）。

### ⑨ 成本结构（eval-cost.js）

**必选维度（评审定案）**：一开始可以粗糙，但不能没有。支持两档：`--cost-basic`（粗粒度：有无成本配置/文档/配额机制）+ `--cost-detailed`（细粒度：具体金额/用量数据）。

| 子维度 | 权重 | 测试方法 |
|--------|------|---------|
| 模型成本透明度 | 40% | 是否暴露模型/API 成本信息（配置或文档）|
| 配额管理 | 30% | 是否有配额监控/预警机制 |
| 成本优化意识 | 30% | 是否有缓存/降级/路由优化配置 |

## 四、综合评分公式（v0.4）

```
内视角 = ①×30% + ②×20% + ③×15% + ④×20% + ⑤×15%   （v0.3 原公式）
外视角 = ⑥×30% + ⑦×30% + ⑧×30% + ⑨×10%

综合分 = 内视角 × 50% + 外视角 × 50%
```

**兼容性**：仅跑内视角（旧命令）时，结果与 v0.3 完全一致；外视角为增量。

## 六、评审问题定案（2026-08-10）

| # | 问题 | 定案 |
|---|------|------|
| 1 | 权重 60/40 还是 50/50？ | **50/50**——内外对等，外部适用性与内在能力同等重要 |
| 2 | 成本结构纳入还是砍掉？ | **纳入**——一开始可以粗糙（粗粒度档），但不能没有 |
| 3 | 生态兼容是否偏袒自家？ | **中立**——不提"优先 OpenClaw"，Hermes / WorkBuddy / Claude Code 等常见框架一视同仁 |
| 4 | 断链恢复的干扰注入是否所有 Agent 接受？ | **可选功能**——默认关闭，由 Agent 自主选择打开 |
