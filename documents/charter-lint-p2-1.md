## 一、要解决的问题

知微审计（2026-11-01）对宪章的判定是：

> **第十四条 90% 的判据是"可编程的规格"，但本仓落地率为 0%**（55 行代码里 0 行涉及 14.x）。这是一份写得极好、一行没实现的规格书。

更尖锐的一条：

> 宪章**唯一自带的可执行资产** `evomap-validate.js` 校验的是"文件在不在、关键词有没有"，**恰好落在 14.10 禁止接受的证据样式上** —— 即宪章自己的校验器不满足宪章自己的证据标准。

P2-1 就是补这一刀：把审计认定的 **12 条强可程序化判据**逐条写成 check。

| 条款 | 判据 | 现在怎么核 |

## 二、三条设计铁律

### ① 三态，不是二态

```
PASS        exit 0   证据齐、判据满足
FAIL        exit 1   判据不满足（真错）
UNDECIDED   exit 2   还判不了（缺证据/缺载体）
```

为什么不合并成「通过/不通过」：

- 把「缺证据」判成 **FAIL** → 人会为了变绿去造假（这是最坏的结果）
- 判成 **PASS** → 假绿，比没有校验器更危险

每个 UNDECIDED 都必须带一句「怎么让它变可判」。当前状态：

```
合计 13 项：✅ 10 · ❌ 0 · ⏸️ 3  · 覆盖率 76.9%
结论 UNDECIDED（exit 2）
  ⏸️ 14.1  18 段尚无指纹锚 → --seal --human <名字>
  ⏸️ 14.4  schema 存在但无历史锚 → --seal 一次建立初始锚
  ⏸️ 14.14 无指纹锚 → --seal --human <名字>
```

三项都卡在同一件事上：**指纹锚只能由人类明示建立**。这不是没做完，这是设计如此（见下条）。

### ② 只吃客观字段，不读语义

每个 check 的证据是哈希、字段名、时间差、探针返回值。
**禁止关键词断言** —— 而这一条由第 13 项判据（`check_meta`）**对校验器自身**执行：扫自己的源码，发现 `evidence_kind: 'keyword'` 就 FAIL。

审计批评旧校验器「关键词算证据」，现在这条批评被写成了代码。

### ③ 无副作用，除 `--seal` —— 而 `--seal` 必须有人名

```bash
$ node scripts/charter-lint.js --seal
❌ 拒绝：--seal 必须带 --human <名字>。
   按 14.12②，C1/C2 的锚定只能由人类明示，不接受沉默或默认同意。
$ echo $?
2
```

**这条拒绝本身就是 14.12① 的可执行证据**：自动程序在能改受保护指纹的那一刻被挡住了。
单测把这条也锁住了（`--seal 无 --human → 拒绝并 exit 2`）。

## 三、自己造的两件工具

### `scripts/write-gate.js` —— 14.12 从"文档里写不许"变成"代码里跑不通"

```js
canWrite({ class: 'C1', actor: 'auto' })                          // false
canWrite({ class: 'C3b', actor: 'auto' })                         // true
canWrite({ class: 'C1', actor: 'human', humanConfirmed: true })   // true
canWrite({ class: 'C1', actor: 'human' })                          // false ← 沉默不算同意
canWrite({ actor: 'auto' })                                        // false ← 不声明级别不给默认值
```

charter-lint 的 14.12① 项**真跑这 5 个探针**。文档里的禁令无法机械核对，探针可以。

### `scripts/record-load-fingerprint.js` —— 14.14 的第二枚指纹

双指纹 = 文件指纹（磁盘）+ 载入指纹（模型实际读到的）。

本脚本的诚实边界（写在文件头，防止被当成"运行时取证"）：

- 它不是从模型上下文里抓的，是**按 `specs/injection-points.json` 里 `mode='a'`（全量拼接）的注入点做确定性重算**
- 对 a 类：全量拼接没有取舍，重算 = 载入
- 对 b 类（检索式召回）：**算不了**，召回集合取决于查询时刻 → 明示列在 `uncovered` 里

输出里 `covers` / `uncovered` 两个字段就是为了不夸大：

```
✅ 载入指纹已记录：4 个 a 类注入点
   未覆盖（b 类/通配）：3 项 —— specs/**、case-studies/**、CHANGELOG.md
```

## 五、旧的 `evomap-validate.js` 怎么办

审计给了两条路：「补成交互式（含前后指纹对照）」或「明确降级为目录卫生检查并改名」。

选了**降级 + 明示**，保留文件名（兼容既有调用）：

```
⚠️ 目录卫生检查通过（11 项存在性断言）
   —— 这**不是**宪章判据校验，也不构成 14.10 证据。
   看判据：node scripts/charter-lint.js
```

一个红着的/名不副实的校验器，比没有校验器更危险 —— 大家会学会忽略它。现在它至少不再冒充证据。

## 七、已知缺口

1. **指纹锚未建立**（3 项 UNDECIDED）—— 需宿主人类执行 `--seal --human <名字>`。这是设计如此，不是遗漏。
2. **14.13.1 三方核验未接**：账本仍在本机。跨机对账（A 核 B、B 核 C）需要对方配合。
3. **14.5b provenance 没实现**：注入点清单声明了必填字段，但召回时挂牌还没落代码。
4. **14.3 三条纯文字承诺**没法程序化（审计也这么判）：非受限方援引 / 不得以没看到为由 / 写证据的手与改东西的手不是同一只 —— 后一条已部分落地（author ≠ modifier），但「同一操作者、同一宿主」的更强分离只能靠外部主体。
